The spec uses RFC 2119 / RFC 8174 keywords. "MUST" and "MUST NOT" are absolute, "SHOULD" and "SHOULD NOT" mean strong recommendations with reasoned-deviation possible, "MAY" / "OPTIONAL" mean truly optional.

---

## Overview

MCP is a JSON-RPC 2.0 protocol between Hosts (LLM applications), Clients (connectors inside hosts), and Servers (services that provide context and tools). Communication is stateful with capability negotiation at initialization.

Features a server may expose: Resources, Prompts, Tools. Features a client may expose to a server: Sampling, Roots, Elicitation.

This document focuses on the slice relevant to building a remote MCP server with Tools.

## Transport: Streamable HTTP

The 2025-06-18 spec defines two standard transports: stdio (subprocess) and Streamable HTTP. Streamable HTTP replaces the older "HTTP+SSE" transport from 2024-11-05.

### Endpoint requirements

> "The server MUST provide a single HTTP endpoint path (hereafter referred to as the MCP endpoint) that supports both POST and GET methods. For example, this could be a URL like https://example.com/mcp."

One path. Both POST and GET handlers required.

### Security: Origin validation and bind address

Verbatim from the Security Warning block:

> "1. Servers MUST validate the Origin header on all incoming connections to prevent DNS rebinding attacks
> 2. When running locally, servers SHOULD bind only to localhost (127.0.0.1) rather than all network interfaces (0.0.0.0)
> 3. Servers SHOULD implement proper authentication for all connections"

Implications for Tasklog:
- Origin header validation MUST be in the MCP server.
- Since our server runs on the phone but receives requests via Cloudflare Tunnel, the effective Origin we see is what Cloudflare forwards. We will validate against an allow-list including `https://claude.ai`.
- Binding: the spec says SHOULD bind to localhost when local. Our case is "exposed via tunnel" rather than "local browser hitting localhost." cloudflared connects out to Cloudflare and forwards to our localhost, so we bind localhost (127.0.0.1) and let cloudflared be the only external entry point. This satisfies the spec's intent and matches our architecture.

### Client-to-server (POST)

> "Every JSON-RPC message sent from the client MUST be a new HTTP POST request to the MCP endpoint."

Required client headers (verbatim):

> "The client MUST include an Accept header, listing both application/json and text/event-stream as supported content types."

Server response decision tree (verbatim):

> "If the input is a JSON-RPC response or notification:
>   If the server accepts the input, the server MUST return HTTP status code 202 Accepted with no body.
>   If the server cannot accept the input, it MUST return an HTTP error status code (e.g., 400 Bad Request). The HTTP response body MAY comprise a JSON-RPC error response that has no id.
> If the input is a JSON-RPC request, the server MUST either return Content-Type: text/event-stream, to initiate an SSE stream, or Content-Type: application/json, to return one JSON object. The client MUST support both these cases."

So: when we get a request (vs a notification), respond with either application/json (single response) or text/event-stream (SSE with the response). For tools/call we can use single-JSON unless we want to stream progress events.

### Server-to-client (optional GET)

> "The client MAY issue an HTTP GET to the MCP endpoint. This can be used to open an SSE stream, allowing the server to communicate to the client, without the client first sending data via HTTP POST."

> "The server MUST either return Content-Type: text/event-stream in response to this HTTP GET, or else return HTTP 405 Method Not Allowed, indicating that the server does not offer an SSE stream at this endpoint."

For Tasklog MVP we likely return 405 for GET. Tools don't need server-pushed messages.

### Session management

The spec defines optional session handling via the `Mcp-Session-Id` header.

> "A server using the Streamable HTTP transport MAY assign a session ID at initialization time, by including it in an Mcp-Session-Id header on the HTTP response containing the InitializeResult."

> "The session ID SHOULD be globally unique and cryptographically secure (e.g., a securely generated UUID, a JWT, or a cryptographic hash). The session ID MUST only contain visible ASCII characters (ranging from 0x21 to 0x7E)."

If we assign a session ID, the client MUST echo it back on subsequent requests. We can choose to operate stateless (no session ID) and that is spec-compliant. For Tasklog MVP, stateless is fine: each call carries an OAuth token and identifies the caller, no session state needed.

### Protocol version header

> "If using HTTP, the client MUST include the MCP-Protocol-Version: <protocol-version> HTTP header on all subsequent requests to the MCP server, allowing the MCP server to respond based on the MCP protocol version."

Example: `MCP-Protocol-Version: 2025-06-18`

> "If the server receives a request with an invalid or unsupported MCP-Protocol-Version, it MUST respond with 400 Bad Request."

We will advertise 2025-06-18 and reject anything we do not support.

## Authorization (OPTIONAL by spec, REQUIRED for claude.ai)

The spec says authorization is OPTIONAL but conditional:

> "Implementations using an HTTP-based transport SHOULD conform to this specification."

If we want claude.ai to connect to us, we MUST implement it. Claude.ai will not connect without OAuth.

### Standards stack the spec mandates

When implementing authorization, the spec defers to the following RFCs:

> "OAuth 2.1 IETF DRAFT (draft-ietf-oauth-v2-1-13)
> OAuth 2.0 Authorization Server Metadata (RFC8414)
> OAuth 2.0 Dynamic Client Registration Protocol (RFC7591)
> OAuth 2.0 Protected Resource Metadata (RFC9728)"

Plus PKCE (RFC 7636) and Resource Indicators (RFC 8707) called out elsewhere in the auth section.

### Roles

> "A protected MCP server acts as an OAuth 2.1 resource server, capable of accepting and responding to protected resource requests using access tokens."

> "An MCP client acts as an OAuth 2.1 client, making protected resource requests on behalf of a resource owner."

> "The authorization server is responsible for interacting with the user (if necessary) and issuing access tokens for use at the MCP server. The implementation details of the authorization server are beyond the scope of this specification. It may be hosted with the resource server or a separate entity."

So we can host the authorization server in the same process as the MCP server (resource server). The spec allows it. That is the simplest deployment for a single-user app.

### Server MUSTs (auth)

Verbatim from "Authorization Server Discovery":

> "Authorization servers MUST implement OAuth 2.1 with appropriate security measures for both confidential and public clients."

> "Authorization servers and MCP clients SHOULD support the OAuth 2.0 Dynamic Client Registration Protocol (RFC7591)."

> "MCP servers MUST implement OAuth 2.0 Protected Resource Metadata (RFC9728). MCP clients MUST use OAuth 2.0 Protected Resource Metadata for authorization server discovery."

> "Authorization servers MUST provide OAuth 2.0 Authorization Server Metadata (RFC8414). MCP clients MUST use the OAuth 2.0 Authorization Server Metadata."

Discovery flow (verbatim sequence diagram source):

```
1. MCP request without token
2. HTTP 401 Unauthorized with WWW-Authenticate header
3. Client extracts resource_metadata from WWW-Authenticate
4. Client GETs /.well-known/oauth-protected-resource
5. Server returns Resource metadata with authorization server URL
6. Client GETs /.well-known/oauth-authorization-server (on the AS)
7. Server returns Authorization server metadata
8. OAuth 2.1 authorization flow happens
9. Client POSTs to /token to exchange code
10. AS returns access token
11. Client makes MCP request with access token
```

WWW-Authenticate is normative:

> "MCP servers MUST use the HTTP header WWW-Authenticate when returning a 401 Unauthorized to indicate the location of the resource server metadata URL"

### PKCE (required)

> "MCP clients MUST implement PKCE according to OAuth 2.1 Section 7.5.2."

In practice, our authorization server MUST advertise support for S256 PKCE and validate the code_verifier on token exchange.

### Resource Indicators (RFC 8707) - the `resource` parameter

> "MCP clients MUST implement Resource Indicators for OAuth 2.0 as defined in RFC 8707 to explicitly specify the target resource for which the token is being requested. The resource parameter:
> 1. MUST be included in both authorization requests and token requests.
> 2. MUST identify the MCP server that the client intends to use the token with.
> 3. MUST use the canonical URI of the MCP server as defined in RFC 8707 Section 2."

Examples of valid canonical URIs (verbatim):

> "https://mcp.example.com/mcp
> https://mcp.example.com
> https://mcp.example.com:8443
> https://mcp.example.com/server/mcp"

### Token usage (Bearer header only, never query)

> "MCP client MUST use the Authorization request header field defined in OAuth 2.1 Section 5.1.1: Authorization: Bearer <access-token>"

> "Note that authorization MUST be included in every HTTP request from client to server, even if they are part of the same logical session."

> "Access tokens MUST NOT be included in the URI query string"

### Token validation (audience binding)

> "MCP servers, acting in their role as an OAuth 2.1 resource server, MUST validate access tokens as described in OAuth 2.1 Section 5.2."

> "MCP servers MUST validate that access tokens were issued specifically for them as the intended audience, according to RFC 8707 Section 2. If validation fails, servers MUST respond according to OAuth 2.1 Section 5.3 error handling requirements. Invalid or expired tokens MUST receive a HTTP 401 response."

> "MCP servers MUST only accept tokens specifically intended for themselves and MUST reject tokens that do not include them in the audience claim or otherwise verify that they are the intended recipient of the token."

### Token passthrough is forbidden

> "MCP clients MUST NOT send tokens to the MCP server other than ones issued by the MCP server's authorization server."

> "If the MCP server makes requests to upstream APIs, it may act as an OAuth client to them. The access token used at the upstream API is a separate token, issued by the upstream authorization server. The MCP server MUST NOT pass through the token it received from the MCP client."

This applies to us only if we ever call upstream APIs on the user's behalf. The Tasklog MCP server calls our own LAN-only Tasklog API which has no auth, so token-passthrough is not a concern.

### Error codes

| Status Code | Description  | Usage                                      |
| ----------- | ------------ | ------------------------------------------ |
| 401         | Unauthorized | Authorization required or token invalid    |
| 403         | Forbidden    | Invalid scopes or insufficient permissions |
| 400         | Bad Request  | Malformed authorization request            |

## Tools

### Server capability declaration

A tool-providing server MUST declare the capability at initialization:

```json
{
  "capabilities": {
    "tools": {
      "listChanged": true
    }
  }
}
```

`listChanged: true` means the server will emit `notifications/tools/list_changed` when the tool set changes. For Tasklog the tool set is static, so we can declare `false` or omit and skip that notification.

### tools/list

Request:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": { "cursor": "optional-cursor-value" }
}
```

Pagination is supported via cursor but only needed if the tool count is large. For Tasklog (around 15 tools) we return all in one page.

Response shape:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "tools": [
      {
        "name": "get_weather",
        "title": "Weather Information Provider",
        "description": "Get current weather information for a location",
        "inputSchema": {
          "type": "object",
          "properties": {
            "location": { "type": "string", "description": "City name or zip code" }
          },
          "required": ["location"]
        }
      }
    ],
    "nextCursor": "next-page-cursor"
  }
}
```

### Tool definition fields

- `name`: unique identifier (string, machine-friendly).
- `title`: optional, human-readable display name.
- `description`: human-readable description of functionality.
- `inputSchema`: JSON Schema for parameters.
- `outputSchema`: optional JSON Schema for structured results.
- `annotations`: optional metadata about behavior.

Annotations carry a security caveat:

> "For trust & safety and security, clients MUST consider tool annotations to be untrusted unless they come from trusted servers."

### tools/call

Request:

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": { "location": "New York" }
  }
}
```

Response (unstructured content):

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "content": [
      { "type": "text", "text": "Current weather in New York: 72F, partly cloudy" }
    ],
    "isError": false
  }
}
```

### Content block types

- `text`: `{ "type": "text", "text": "..." }`
- `image`: `{ "type": "image", "data": "<base64>", "mimeType": "..." }`
- `audio`: `{ "type": "audio", "data": "<base64>", "mimeType": "..." }`
- `resource_link`: link to a server resource
- `resource`: embedded resource

For Tasklog tools, text content is sufficient.

### Structured content (optional)

If a tool declares an `outputSchema`, the response SHOULD include `structuredContent` matching that schema. For backwards compatibility, also include the JSON-serialized form in a text block.

### Error handling: two mechanisms

> "Tools use two error reporting mechanisms:
> 1. Protocol Errors: Standard JSON-RPC errors for issues like: Unknown tools, Invalid arguments, Server errors
> 2. Tool Execution Errors: Reported in tool results with isError: true: API failures, Invalid input data, Business logic errors"

Protocol-error example:

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "error": { "code": -32602, "message": "Unknown tool: invalid_tool_name" }
}
```

Tool-execution-error example:

```json
{
  "jsonrpc": "2.0",
  "id": 4,
  "result": {
    "content": [
      { "type": "text", "text": "Failed to fetch: API rate limit exceeded" }
    ],
    "isError": true
  }
}
```

For Tasklog: a 404 from the upstream API translates to an isError tool result, not a JSON-RPC protocol error. Protocol errors are reserved for unknown tool names and malformed JSON-RPC.

### Server MUSTs (tools)

> "1. Servers MUST:
>    Validate all tool inputs
>    Implement proper access controls
>    Rate limit tool invocations
>    Sanitize tool outputs"

## Server MUSTs checklist (everything we owe the spec)

A condensed checklist for the implementation, drawn from the sections above:

- [ ] Single MCP endpoint path, POST and GET methods.
- [ ] Origin header validation against an allow-list (DNS rebinding defense).
- [ ] Accept header negotiation: respond with application/json or text/event-stream as appropriate.
- [ ] MCP-Protocol-Version header validation; reject unsupported versions with 400.
- [ ] WWW-Authenticate header on 401 responses pointing to /.well-known/oauth-protected-resource.
- [ ] /.well-known/oauth-protected-resource endpoint (RFC 9728).
- [ ] /.well-known/oauth-authorization-server endpoint (RFC 8414).
- [ ] OAuth 2.1 authorization + token endpoints supporting PKCE S256.
- [ ] DCR endpoint (POST /register) per RFC 7591 (SHOULD - claude.ai prefers it).
- [ ] Access token audience validation; reject tokens not issued for our canonical URI.
- [ ] Bearer header only; reject query-string tokens.
- [ ] tools/list and tools/call JSON-RPC methods.
- [ ] Validate tool inputs against inputSchema.
- [ ] Distinguish protocol errors (unknown tool, bad JSON-RPC) from tool execution errors (isError: true).

## Open questions / gaps

These are items the research did not cover and which we will resolve during `/create-plan` or `/execute`:

1. **Initialization handshake** - the lifecycle/initialize message format (capabilities exchange) was not captured here. See `/specification/2025-06-18/basic/lifecycle` to fill in.
2. **Authorization server metadata exact JSON shape** - RFC 8414 defines fields like `issuer`, `authorization_endpoint`, `token_endpoint`, `registration_endpoint`, `code_challenge_methods_supported`, `grant_types_supported`. We will copy a working example from a reference implementation.
3. **Protected resource metadata exact JSON shape** - RFC 9728 fields including `resource`, `authorization_servers`, `scopes_supported`, `bearer_methods_supported`. Same approach: reference implementation.
4. **TypeScript SDK coverage** - `@modelcontextprotocol/sdk` provides server primitives. Need to verify which of the above MUSTs it handles automatically vs which we implement manually.
5. **Streaming for long-running tools** - Tasklog tools are short (single SQLite query). We do not need SSE responses for tools/call. If we ever add a long-running tool, revisit.
